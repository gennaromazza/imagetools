# Archivio Flow
## Architecture & Ingest Workflow Refactor Specification

> **Documento operativo per Codex**
>
> Questo documento descrive una revisione architetturale di StudioFlow / Archivio Flow.
>
> Non trattare le sezioni seguenti come una lista di patch UI indipendenti.
>
> L'obiettivo è riprogettare il dominio **Archive / Media Ingest / SD Tracking / Import Verification / Remote Registry** in modo coerente, persistente, recuperabile e verificabile.

---

# 0. Obiettivo

StudioFlow deve evolvere da:

```text
SD
↓
selezione cartella
↓
copia file
```

a:

```text
SD
↓
rilevamento
↓
analisi contenuto
↓
riconoscimento scheda/sessione
↓
confronto con storico
↓
selezione lavoro
↓
risoluzione automatica destinazione
↓
preflight
↓
importazione
↓
verifica
↓
registrazione manifest
↓
aggiornamento archivio
↓
sync registro remoto
↓
verifica futura
```

Il sistema deve poter rispondere in maniera affidabile a due domande fondamentali:

> **Dove devono essere importate queste fotografie?**

e soprattutto:

> **Queste fotografie sono realmente già al sicuro nel mio archivio?**

La seconda domanda è critica perché può determinare se una scheda SD possa essere formattata.

# 1. PRINCIPI ARCHITETTURALI OBBLIGATORI

## 1.1 Local-first

La fonte primaria dei dati deve essere locale.

```text
                    ┌──────────────────────┐
                    │      StudioFlow      │
                    └──────────┬───────────┘
                               │
                               ▼
                    ┌──────────────────────┐
                    │   LOCAL DATABASE     │
                    │       SQLite         │
                    └──────────┬───────────┘
                               │
               ┌───────────────┼────────────────┐
               │               │                │
               ▼               ▼                ▼
         Archive Index    Import Registry   Sync Queue
                                                │
                                                ▼
                                      ┌─────────────────┐
                                      │  Google Drive   │
                                      │ Remote Registry │
                                      └─────────────────┘
```

Google Drive NON deve essere necessario per:

- aprire StudioFlow;
- consultare l'archivio;
- importare;
- verificare duplicati;
- completare una Import Session;
- usare l'app offline.

Drive è esclusivamente:

```text
replica remota leggera
```

del registro locale.

# 2. DECISIONE PREFERENZIALE SULLA PERSISTENZA

La soluzione preferenziale è:

```text
SQLite
```

e non un singolo file JSON globale.

Il JSON può essere utilizzato per:

- configurazioni;
- export;
- interoperabilità;
- piccoli manifest;
- snapshot;
- debug;
- eventuale metadata opzionale scritto sulla SD.

Non deve invece diventare il database principale dell'applicazione.

## Motivazioni

Il dominio richiede:

- aggiornamenti incrementali;
- migliaia o milioni di record file;
- relazioni tra lavori, schede e importazioni;
- query;
- indici;
- transazioni;
- aggiornamenti concorrenti;
- recupero dopo crash;
- migrazioni;
- sincronizzazione;
- storico.

SQLite è quindi il candidato naturale.

### Vincolo

Prima dell'implementazione verificare se nel repository esiste già:

- SQLite;
- altro database embedded;
- persistence layer;
- repository abstraction.

Se esiste già una soluzione equivalente e tecnicamente valida, riutilizzarla.

Non introdurre una seconda tecnologia senza necessità.

# 14. FILE FINGERPRINT

Non utilizzare solamente:

```text
filename
```

come identità di una fotografia.

Filename come:

```text
DSCF0001.RAF
DSC_0001.NEF
A0012345.ARW
```

possono ripetersi.

Implementare fingerprint progressivo.

---

# 15. STRATEGIA DI FINGERPRINT

## Livello 0 — Discovery

Raccogliere:

```text
relativePath
filename
extension
size
mtime
```

Costo minimo.

---

## Livello 1 — Fast signature

Combinare elementi come:

```text
size
extension
selected metadata
partial hash
```

Il partial hash può utilizzare blocchi del file anziché leggere tutto.

Esempio concettuale:

```text
first 64KB
+
middle 64KB
+
last 64KB
```

Hash con algoritmo veloce appropriato.

---

## Livello 2 — Full hash

Calcolare hash completo esclusivamente quando necessario:

- collisione;
- verifica critica;
- file ambiguo;
- policy esplicita.

Non calcolare SHA-256 di ogni RAW da 60-100 MB durante ogni scansione se non necessario.

---

# 16. CARD CONTENT FINGERPRINT

Non leggere completamente gigabyte di fotografie soltanto per capire se una SD è stata vista.

Creare un fingerprint deterministico del contenuto basato sul manifest.

Esempio concettuale:

```text
normalize(
    relativePath
    + size
    + fastFingerprint
)
```

ordinare deterministicamente i record e calcolare:

```text
cardContentFingerprint
```

Il fingerprint deve cambiare se cambia significativamente il contenuto.

# 20. RESUME DOPO INTERRUZIONE

Se l'app viene:

- chiusa;
- terminata;
- aggiornata;
- crasha;

oppure se:

- viene rimossa la SD;
- si disconnette il disco;
- manca spazio;

la sessione deve poter essere recuperata.

All'avvio:

```text
SELECT import_sessions
WHERE status IN (
    'IMPORTING',
    'VERIFYING',
    'INTERRUPTED'
)
```

e offrire:

```text
Riprendi importazione
```

senza ricopiare automaticamente i file già verificati.

---

# 21. SCRITTURE ATOMICHE

Durante la copia evitare che file incompleti appaiano come fotografie valide.

Preferire:

```text
destination/file.RAF.studioflow-part
```

e solo dopo copia + verifica:

```text
rename atomic
↓
destination/file.RAF
```

Se supportato dal filesystem.

---

# 22. VERIFICA POST-COPY

Per ogni file importato verificare almeno:

```text
source size == destination size
```

e la fast signature prevista.

Per livelli di sicurezza superiori utilizzare hash completo.

Un file non verificato:

```text
COPIED
```

non equivale a:

```text
VERIFIED
```

---

# 23. IMPORT MANIFEST

Ogni Import Session completata deve generare un manifest logico.

Non necessariamente un file separato: può essere derivato dal DB.

Concettualmente deve contenere:

```text
session
card snapshot
job
destination
files
fingerprints
timestamps
verification status
```

Il manifest è la prova storica dell'importazione.

---

# 24. QUANDO UN'IMPORTAZIONE È COMPLETATA

Una sessione può diventare:

```text
COMPLETED
```

solo quando:

```text
plannedFiles ==
verifiedFiles
+
acceptedDuplicates
+
explicitlySkippedFiles
```

e non esistono errori bloccanti.

Questa regola deve essere centralizzata.

Non duplicare questa logica nella UI.

# 98. CRITERI DI ACCETTAZIONE

La feature è accettabile solo se soddisfa almeno quanto segue.

---

## Startup

- [ ] StudioFlow mostra l'ultimo indice conosciuto senza attendere full scan.
- [ ] La verifica dell'archivio avviene in background.
- [ ] La UI mostra stato/progresso.
- [ ] Full scan non parte inutilmente ad ogni startup.

---

## Archive mapping

- [ ] Esiste un archive root configurato.
- [ ] Le categorie hanno mapping persistente.
- [ ] La destinazione viene calcolata automaticamente.
- [ ] È possibile fare override manuale.

---

## SD

- [ ] Una SD viene rilevata senza dipendere dalla drive letter.
- [ ] Stesso supporto con contenuto nuovo viene riconosciuto come snapshot differente.
- [ ] È possibile riconoscere file nuovi su una scheda già utilizzata.

---

## Import

- [ ] Ogni import ha una sessione persistente.
- [ ] Ogni file ha stato persistente.
- [ ] Un crash non obbliga a ricopiare tutto.
- [ ] File incompleti non risultano completati.
- [ ] La sessione viene completata solo dopo verifica.

---

## Duplicati

- [ ] Stesso nome non significa automaticamente stesso file.
- [ ] La duplicate detection utilizza fingerprint.
- [ ] Hash completi vengono utilizzati solo quando necessari.

---

## Safe To Format

- [ ] SAFE richiede verifica deterministica di tutti i file rilevanti.
- [ ] Un solo file non verificato impedisce SAFE.
- [ ] Stesso volume serial non è sufficiente.
- [ ] Bloom Filter non è sufficiente.
- [ ] Incertezza produce UNKNOWN/UNSAFE, mai SAFE.

---

## Google Drive

- [ ] Nessuna fotografia viene caricata.
- [ ] L'import funziona completamente offline.
- [ ] Un errore Drive non invalida un'importazione verificata.
- [ ] Esiste retry.
- [ ] I percorsi remoti sono relativi.
- [ ] Il formato remoto è versionato.
- [ ] Viene riutilizzata l'integrazione esistente se appropriata.
